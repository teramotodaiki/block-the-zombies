# アーキテクチャ設計（core と Phaser の分離）

## レイヤ構造

大きく 3 層に分ける：

1. core 層
   - ゲームルール・シミュレーション・レベルデータの扱い。
   - Phaser や DOM に依存しない純粋なロジック。
2. engine 層
   - Phaser 上での描画・入力・アセットロード。
   - core 層の状態を読み、画面に反映する。
3. app／UI 層
   - シーン遷移（タイトル→マップ→レベル→クリア）。
   - UI の配置（HUD のボタン・インベントリ表示など）。

理由：
- core 層を分けることで、ロジックを単体テストしやすくするため。
- AI コーディングで core 層に対する変更を安全に行いやすくするため。
- Phaser のバージョン変更などがあっても、core 層を極力触らずに済むようにするため。

## データフロー（抽象）

- core：
  - ステージ開始時に「レベル定義（LevelConfig 相当）」を受け取り、ゲーム状態を初期化する。
  - 経過時間を受け取り、内部状態を進める（例：`update` に相当する処理を持つ）。
  - 入力（タップ）を「フィールド座標でのブロック操作指示」として受け取るインターフェイスを持つ。
- engine (Phaser)：
  - 描画のたびに core の現在状態（タイル・エンティティ・ブロック・ゴール進捗など）を読み取り、スプライトに反映する。
  - 画面タップ座標からフィールドのグリッド座標を計算し、core に「ブロック設置/破壊のリクエスト」を送る。
- app：
  - どのレベルを遊ぶか・どのバイオームかを管理する。
  - シーンの切り替え時に「どのレベル定義を core に渡すか」を決める。

## 依存関係のルール

- core 層は Phaser やブラウザ API を一切知らない。
- engine 層は core 層の公開インターフェイスにのみ依存する。
- app 層は core と engine の両方を組み合わせるが、
  core の内部構造（状態の詳細な構造）には直接依存しないようにする。

理由：
- 依存方向を一方向にしておくことで、
  将来の変更範囲を局所化しやすくするため。
- core 層のテストを Node 上で実行し、ブラウザを立ち上げずに検証できるようにするため。
