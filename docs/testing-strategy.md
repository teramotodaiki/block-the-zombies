# テスト方針・対象仕様

## テストの優先度

- 最優先：
  - core 層のロジック（移動・ブロック設置判定・勝敗判定）。
  - レベル定義の基本的な整合性チェック（寸法・タイル数など）。
- 次点：
  - レベルごとの簡易シミュレーション（極端な詰みの検出）。
- 任意：
  - UI のスナップショットテスト。
  - E2E テスト（必要であれば後で追加）。

理由：
- core のバグは全レベルに波及しやすいため。
- レベル定義は AI にも書かせるため、人間のレビューだけに頼れないため。

## core ロジックのテスト例（抽象）

- 村人移動：
  - 1 段の段差は登れるが、2 段は登れないこと。
  - 前方にブロックがあれば反転すること。
- ブロック設置：
  - 隣接ブロックがない場所には置けないこと。
  - 上限数到達後には置けないこと。
  - 壊すと再び置けること。
- 勝敗判定：
  - ゴール位置に一定数到達したらクリアになること。

## レベルバリデーション方針（抽象）

- 静的チェック：
  - タイル配列の長さと width×height が一致しているか。
  - スタート位置・ゴール位置がステージ内に収まっているか。
  - ブロック上限値が合理的な範囲か（例：極端な 0 や数百などは弾く）。
- 簡易シミュレーション（任意だが推奨）：
  - ブロック操作なしの状態で数秒シミュレーションし、
    - 即全滅
    - 即クリア
    を検出して警告する。

理由：
- レベル追加時に CI が落ちることで、
  明らかに壊れたレベルが main ブランチに入るのを防ぐため。
- テストを「すべての状態を保証するもの」ではなく、
  「明らかなミスを早期に気付くためのもの」と位置づけるため。
